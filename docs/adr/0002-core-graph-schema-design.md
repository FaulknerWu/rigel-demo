# ADR-0002: 核心语义图谱架构设计

> 说明：本文档记录目标图谱 Schema 与检索链路。当前 `core/src/model.rs` 仍保留早期占位结构，尚未完全落地本 ADR。

## 状态
已接受 (Accepted)

## 背景
在初期的设想中，可解释代码语义检索系统常常依赖细粒度的文件、类型与可调用方法（AST 取向）以及高度细分的关系种类构建代码图谱。然而，这种贴近“抽象语法树”或编译器的建模方式会导致：
1. **图数据库极度庞大**：存储全量代码特征与细粒度语法关系容易使图空间激增，从而影响大范围多跳查询性能。
2. **缺乏宏观聚合**：Agent在实际使用中更多时候需要的是宏观语义导航（如文件级依赖、核心实体依赖），而非微观 Token 或 AST 的导航。
3. **架构复杂度过高**：如果试图在第一版就囊括增量更新、快照多版本管理，开发复杂度将难以控制，且容易偏移验证检索结果可用性这一核心目标。

## 决策
1. **代码原文剥离图数据库**：图数据库中不再保留代码内容本体。相关代码仍存在原始存储中，图区仅保留节点身份（Identity）、关系拓扑（Relations）、版本哈希（Hashes）、摘要（Summaries）以及定位用的位置锚点（Anchors）。用到原文时进行懒加载。
2. **重塑粗粒度节点体系**：将图数据库节点划分为基础设施、物理结构与核心语义 3 个层次。明确确立 Repository、Module、File、Entity、Anchor、Summary 六类核心节点，废弃原有的 file、type、callable 等强语言绑定节点概念。
3. **收敛核心关系族**：避免构建数百种细分关系，将图的连接限定为 6 大顶级关系：`CONTAINS`, `DEPENDS_ON`, `SPECIALIZES`, `ALIASES`, `HAS_ANCHOR`, `DESCRIBES`。具体的调用、继承差异通过边关联的属性（如 `kind` 和 `confidence`）进行下钻区分。
4. **统一检索链路**：确立 语义召回 (Recall) -> 锁定种子 (Seed targeting) -> 图谱扩充 (Expansion) -> 组装返回 (Assembly) 为标准的数据读取架构。
5. **降级并推迟增量与版本并发**：一期架构仅支持以**离线全量静态方式**索引代码库。将原有的多快照版本隔离（Snapshot）以及增量索引构建计划移出本次工程边界，留作独立的里程碑专项设计。

## 决策依据

### 为什么选择原文剥离与粗粒度优先
* **减负图数据库**：图数据库的核心专长在于关系多跳遍历。去掉大段原文字符串能极大减少存储与内存负担，让运算资源集中在拓扑搜索中。
* **贴合 LLM 视角**：大模型通常基于更高维度的抽象与概念（类、对象、模块职能）进行理解，保留宏观节点更利于映射出 Agent 易读的执行流。
* **懒加载更加精准**：通过单独的 Anchor 进行跨架构寻址，有助于前端展示或后续精准截取需要的切片，不必在图里来回传输大块长文本。

### 为什么收敛为 6 大边族
* **减少 Cypher 撰写开销**：如果在定义、依赖与实现上分划几十种关联关系，会给泛化搜索与代码拓展极高的复杂度。关系抽象为一个统一类型（如：`DEPENDS_ON`），将大大减少图库的模式（Schema）体积与编写查询语句的心智负担。同时属性 `kind` 还能完美承接特定语言（如 Java）才有的特定调用关系名。

### 为什么推迟增量与快照设计
* **控制开发节奏**：全量静态解析能够以最快速度打通整条链路，从而暴露整个检索召回阶段的短板。过早引入图内垃圾回收机制、增量差异比对算法以及多快照并发管理反而会导致系统在最初期就结构僵化，得不偿失。

## 影响

### 正向影响
* **显著提高了系统的查询性能与容量**：去原文后的轻量化模型能在同样的内存下吞吐更大的仓库数据。
* **搜索过程可解释**：依靠宏观节点组成的导航树配合专门为搜索打造的 Summary，路径解释更加自然。
* **集中注意力解决最硬性需求**：放弃增量等特性，当前开发资源能高度集中在准确无误提取 AST 等实体属性及完善混合向量召回率的问题上。

### 负向影响
* **请求被切分为两环**：下游 Agent 被迫需要处理二次发包（第一发根据自然语言走图获得实体和 Anchor，第二次根据 Anchor 通过文件系统拉取实际文本）。
* **大型重构开支**：在将来面临“单库上亿行代码”以及极频繁更新的场景下，因为缺乏增量构建机制，每一次微小更改都必须执行耗时较久的整体静态重算。这一架构欠债会被留到后续版本强制偿还。
