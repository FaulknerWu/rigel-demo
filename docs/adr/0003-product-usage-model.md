# ADR-0003: 产品使用形态与本地 CLI 工作流设计

## 状态
已接受 (Accepted)

## 背景
Rigel 的核心价值是把代码仓库转化为可查询、可解释、可对话的语义图谱。早期产品形态主要围绕 MCP 接入 Agent 展开：Agent 通过 MCP 工具访问代码图谱，完成路径分析、调用关系追踪、依赖解释与上下文召回。

但如果只提供 MCP 形态，会带来以下限制：
1. **使用门槛偏高**：用户需要先理解 MCP、配置 Agent、维护服务生命周期，才能体验代码图谱能力。
2. **本地数据归属不清晰**：代码图谱运行时如果完全依赖外部服务，用户难以直观看到当前仓库对应的数据文件与初始化状态。
3. **演示链路不完整**：仅通过 Agent 对话展示图谱能力时，缺少可视化反馈，难以让用户快速理解图谱结构、节点关系与查询结果来源。
4. **后续产品复用不足**：如果 MCP 与 CLI 各自维护独立初始化逻辑，会造成配置、索引、存储路径与图谱生命周期管理重复实现。

因此，需要明确 Rigel 除 MCP 外的本地 CLI 使用形态，并让 MCP 复用同一套初始化、索引与本地存储流程。

## 决策
1. **同时支持 MCP 与 CLI 两种产品入口**：Rigel 不只作为 MCP Server 接入 Agent，也会打包为独立 CLI 工具。CLI 是本地仓库初始化、索引构建、图谱存储与调试体验的主入口；MCP 是 Agent 使用同一份图谱能力的协议入口。
2. **CLI 默认面向当前文件夹工作**：用户在任意代码仓库根目录执行初始化命令后，Rigel 会以当前文件夹作为目标 Repository，生成本地工作目录，并把运行时数据放入该仓库的子目录中。
3. **本地图数据库文件落在仓库子目录**：初始化后，CLI 会在当前仓库下创建 Rigel 专用目录，并在其中生成 FalkorDBLite 数据文件。该文件代表当前仓库的本地图谱状态，便于用户理解、迁移、清理与复现。
4. **MCP 复用 CLI 初始化流程**：后续 MCP Server 不单独发明一套项目发现、索引构建与数据库定位逻辑，而是基于 CLI 已定义的本地工作目录、配置、索引产物与 FalkorDBLite 文件运行。
5. **Demo 仓库额外提供 Web 可视化入口**：本 `rigel-demo` 仓库在 CLI 启动后，可以额外生成或启动一个 Web 页面。页面左侧展示代码图谱可视化视图，右侧提供与 LLM 对话的 Chat 界面，用于演示自然语言问题如何映射到图查询与代码上下文分析。

## 决策依据

### 为什么需要 CLI 产品形态
* **降低首体验成本**：CLI 符合开发者对本地工具的直觉。用户只需要进入项目目录并执行初始化命令，就能得到当前仓库的图谱文件与后续查询入口。
* **明确本地状态边界**：把 FalkorDBLite 文件生成在当前仓库子目录下，可以让用户清楚知道图谱属于哪个代码库，也避免多个项目之间的数据状态混淆。
* **便于自动化集成**：CLI 更容易被脚本、CI、本地任务运行器或编辑器插件调用。MCP 可以专注服务 Agent，而不是承担所有初始化职责。

### 为什么 MCP 要复用 CLI 流程
* **避免双轨实现**：如果 MCP 与 CLI 分别处理初始化、索引和数据库定位，后续任何 Schema、路径或配置变更都需要同步修改两套逻辑。
* **保证结果一致**：同一仓库在 CLI、MCP 与 Web Demo 中看到的图谱应来自同一份 FalkorDBLite 数据文件，避免“命令行能查到、Agent 查不到”这类割裂体验。
* **利于演进**：未来从 FalkorDBLite 切换到远程 FalkorDB 或增加增量索引时，只需要升级底层工作流，MCP 与 Web Demo 可以自然继承能力。

### 为什么 Demo 需要 Web 页面
* **增强可解释性**：图谱能力天然适合可视化。左侧图视图能展示节点、边、路径与聚类关系，右侧 Chat 能展示 LLM 如何基于图谱回答问题。
* **强化演示闭环**：用户可以先看到整体图结构，再通过自然语言问题触发路径分析、递归函数查找、热门方法统计、调用者追踪等操作。
* **区分产品主线与演示增强**：Web 页面是 `rigel-demo` 的演示能力，不强制成为所有生产部署的默认形态。正式产品仍以 CLI 初始化流程和 MCP 协议入口作为稳定基础。

## 影响

### 正向影响
* **产品入口更完整**：CLI 面向本地开发者，MCP 面向 Agent，Web Demo 面向可视化演示，三者职责清晰且可以复用底层图谱流程。
* **本地运行更自洽**：FalkorDBLite 文件随仓库子目录生成，降低环境配置成本，也方便清理、重建与问题复现。
* **后续开发更集中**：CLI 成为初始化与索引流程的单一事实来源，MCP 和 Web Demo 不需要重复实现仓库发现与数据库管理逻辑。
* **演示效果更直观**：Web 页面能同时呈现代码图谱和 LLM 对话，帮助用户理解 Rigel 的“图谱 + Agent”价值。

### 负向影响
* **CLI 生命周期管理复杂度上升**：需要明确初始化、重建、启动、停止、清理等命令边界，并处理本地目录已存在、数据库文件损坏或索引版本不一致等情况。
* **仓库目录会产生运行时文件**：用户需要理解 Rigel 专用子目录的用途，并在必要时将其加入 `.gitignore`，避免误提交本地图谱数据。
* **Demo 与正式产品边界需要持续维护**：Web 页面服务于演示体验，不能反向绑架 CLI 与 MCP 的稳定接口设计。
* **本地文件模式不等于生产部署模式**：FalkorDBLite 适合单机本地仓库与演示场景。多人共享、远程协作或高并发使用时，仍需要切换到远程 FalkorDB 或其他正式运行时方案。
