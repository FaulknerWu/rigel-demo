# ADR-0001: 技术栈选型

> 说明：本文档记录已接受的技术方向。当前仓库仅完成部分脚手架，文中的目标能力并不都已落地。

## 状态
已接受 (Accepted)

## 背景
Rigel 项目的核心业务域包含两个差异显著的技术负载：
1. **基础设施负载**：包含全量静态代码解析（Tree-sitter）、跨文件代码依赖拓扑构建、数据状态管理，以及作为长期运行的本地 MCP (Model Context Protocol) Server 暴露服务。（注：基于最新 ADR 决策，原定的增量索引支持已推迟）此类负载要求高并发安全性、低内存占用以及与底层 C 库（Tree-sitter 核心）的高效交互。
2. **AI 语义负载**：包含代码语义摘要生成、查询改写、文本向量化（Embedding）以及检索增强生成（RAG）。此类负载的交互模式为固定管线和确定性输入输出，但需要高频的 Prompt 调优、评估集比对和参数验证。

## 决策
1. **主项目语言选取 Rust**：索引引擎、解析适配层、图结构计算、检索重排逻辑以及 MCP Server 全部使用 Rust 实现。
2. **设立 Python 实验台**：仅使用 Python 作为离线实验工作台，负责 Prompt 调优、评估（Evaluation）、数据集构建与基准测试，禁止 Python 代码进入生产主链路。
3. **自建轻量级 AI 接入层**：不在主项目中引入 LangChain 等重型框架代码。Rust 端仅实现基础的 LLM API 客户端、Prompt 模板渲染与结构化输出解析校验。
4. **采用 Monorepo 仓库管理**：将 Rust 生产代码、Python 实验代码及跨语言共享资产统一存放在单代码仓库中。
5. **基于规格协议的跨语言协作**：Python 与 Rust 之间不传递执行逻辑，仅通过中立格式（JSON/YAML/JSON Schema）共享 Prompt 模板、评估集和输出数据结构声明。
6. **图数据库选型为 FalkorDB**：将 FalkorDB 作为 Rigel 的主图存储，承载代码实体、关系边、全文检索索引、向量检索索引及图遍历查询。

## 决策依据

### 为什么主项目选择 Rust
* **解析层原生契合**：Rigel 强依赖 Tree-sitter，该组织官方提供 Rust 绑定，解析引擎层的集成最为完善。
* **内存与状态控制**：系统涉及庞大的 AST 节点遍历、图数据库缓存和后续可能引入的增量更新。Rust 的所有权模型与类型系统能有效在编译期规避复杂的并发状态冲突与内存安全问题。
* **性能与资源占用**：作为本地常驻服务（MCP Server），Rust 提供可预测的低延迟与低内存占用，符合基础设施工具的长期演进目标。

### 为什么 AI 模块采用“Python实验 + Rust自建基座”
* **AI 交互模式简单**：需求文档（PRD）中的 AI 功能（摘要、改写、回答）均为线性管线，不涉及复杂的开放式 Agent 路由或多轮动态工具调用。自建 Rust AI 接入层足以覆盖需求，无需引入 LangChain 的框架复杂度。
* **分离关注点**：Python 提供无可替代的模型评估、调试与数据处理生态（如各类 Evaluator 库）。将其限定在实验边界内，既能利用其生态优势加速算法选型，又不会将其动态类型与运行时开销带入核心解析链路。

### 为什么采用 Monorepo
* **版本一致性**：实验结论（Prompt 版本、Schema 定义）需要与生产代码严格同步。分离仓库易导致协议版本漂移。Monorepo 确保每次提交时，评估集与实际消耗该评估集的 Rust 业务逻辑保持一致。

### 为什么图数据库选择 FalkorDB
* **最贴合当前核心查询形态**：FalkorDB 原生提供属性图、Cypher 查询、向量索引和全文索引，更贴合代码图谱检索主链路。
* **Rust 接入成本可控**：相比更偏 JVM 服务生态的方案，FalkorDB 对 Rust 主链路更友好，能够在不引入额外中间层的前提下完成索引写入、检索查询和图遍历执行。
* **图、全文、向量能力集中在同一底座**：Rigel 的索引系统要求实体、摘要、Embedding 和边关系始终保持一致。将这些能力放在同一数据库中，有利于降低同步复杂度，避免多存储之间的数据漂移和一致性治理成本。

### 为什么不选择其他候选
* **不选择 PostgreSQL + pgvector**：其全文与向量能力成熟，但图遍历不是一等公民；若将其作为唯一主库，复杂关系扩展和路径查询会被迫下沉到应用层或递归 SQL，长期会将图查询复杂度转移到业务代码中。
* **不选择 Neo4j**：Neo4j 的图能力成熟，但整体更偏独立服务与团队化运维形态，Rust 生态也不是官方一等公民。对 Rigel 当前“Rust 本地主链路”的形态来说，接入与运行成本不如 FalkorDB 直接。
* **不选择 Kuzu**：Kuzu 的嵌入式形态曾与项目方向高度匹配，但官方仓库已于 2025-10-10 存档。
* **不选择 HelixDB**：HelixDB 虽然方向接近，但生态和查询语言仍较新。

## 影响

### 正向影响
* **系统稳定性极高**：Rust 承担核心链路，确保了索引阶段的性能上限与并发安全性。
* **架构纯度高**：主系统免受外部庞大 AI 框架的侵入，保留了基础设施项目的轻量与可控。
* **迭代效率隔离**：算法实验与工程实现解耦，便于不同职责的开发任务并行开展。
* **检索链路更统一**：图遍历、全文召回、向量召回和证据聚合落在同一数据底座中，能够降低跨系统拼装查询的复杂度。
* **数据库演进路径更平滑**：后续即使新增业务库或对象存储，也只是在主图数据库外围扩展能力，不需要更换核心索引底座。

### 负向影响
* **MCP SDK 限制**：目前官方 MCP Rust SDK 仅处于 Tier 2 级别。应对方案：评估现有 SDK 的完整度，必要时需投入少量精力处理协议层的边角问题。
* **本地 Embedding 阻碍**：若后期需要脱离云端 API 进行本地文本向量化，Rust 需处理 ONNX 运行时 FFI 绑定，工程复杂度高于 Python。
* **数据库能力绑定更强**：核心查询将围绕 FalkorDB 的图模型与索引能力设计，后续如需迁移到底层能力差异较大的数据库，迁移成本会较高。
* **需要尽早收敛 Schema 与索引策略**：由于图结构、全文索引和向量索引会共同参与检索排序，实体建模、边类型拆分和索引粒度需要在早期就统一约束。
